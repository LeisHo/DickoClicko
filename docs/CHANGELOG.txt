2026-09-01  -  10:33 PM - 10:49 PM EDT

Initial build, from a spec given as a *DEV*/*COL* shorthand list (documented
in CLAUDE.md). Single-file HTML/canvas app: a circle anchors a rope
simulated with verlet-integration point-chain physics (gravity, distance
constraints, per-segment thickness/curved end cap). All position/size dev
controls use %/vmin of the viewport rather than px, per explicit
requirement, so the layout stays proportional on both desktop and mobile.

Added:
- Circle rendering (%-based size/position, color picker).
- Rope rendering hanging from the circle center, curved (rounded-cap +
  filled end-arc) rather than a flat line.
- Verlet rope physics: gravity strength, rope weight, and animation-speed
  dev controls; the anchor point is re-pinned to the circle's position
  every frame.
- Click/punch interaction: clicking on or near the rope applies a
  directional impulse (away from the click point, tapered across
  neighboring points) so the rope deforms and swings back to equilibrium
  pendulum-style, rather than moving as a rigid stick.
- Click-and-hold to continuously grow the rope's length at a dev-controlled
  rate.
- Double-click to cut the rope at that point; the lower piece becomes an
  independent falling physics body inheriting velocity at the moment of the
  cut. Double-click is hand-rolled (setTimeout-based, keyed off the
  Double Click Threshold dev control) rather than the native dblclick
  event, specifically so a double click never fires a single-click punch
  first, per explicit requirement.
- Floor: toggle, color, thickness, and height dev controls; cut pieces
  collide with the floor and pile on each other via pairwise point
  repulsion across all fallen pieces.
- Full dev panel: collapsible *COL* groups, every *DEV* from the spec
  wired to a live effect, color pickers for color-only controls, and every
  slider's numeric readout independently editable to any value beyond the
  slider's own min/max (the slider handle visually clamps; the real value
  is used by the sim).
- Dev-mode gating: shows the panel on file://, localhost/127.0.0.1, or
  ?dev=1; hidden otherwise.
- Project docs (README, PROJECT_SUMMARY, CODE_SUMMARY, PROJECT_PROGRESS)
  and a project CLAUDE.md documenting the *DEV*/*COL* prompt shorthand and
  the future-default-value +20%-max-expansion convention.

Fixed:
- A cut rope piece falling from a perfectly vertical, undisturbed hanging
  rope has no asymmetry to topple over on -- it was standing on the floor
  as a rigid straight column instead of settling into a heap. Found via
  direct physics-state inspection (stepping the simulation and reading
  point positions), not visually. Fixed by giving each cut piece a small
  random initial tilt (rotated around its own cut-point end) at the moment
  of cutting, so gravity and the floor collision naturally fold it into a
  heap.
- The Rope Length slider had no effect once the rope's segment length was
  intentionally decoupled from cfg.ropeLength (needed so hold-to-grow and
  cutting could change the rope's effective length without a later
  slider-default read snapping it back to the full default) -- added an
  onChange hook so manually dragging the slider still rescales the rope's
  current length correctly, including on an already-cut remainder.

Verified:
- All physics behaviors (anchor pin/stability, punch in both directions
  described in the spec, hold-to-grow rate matching the dev control
  exactly, double-click-cut point count and no spurious single-click punch
  firing first, floor collision, multi-piece pile repulsion pushing
  overlapping points apart) via direct calls into the running page's
  physics functions through javascript_tool, stepping frames manually --
  this session's headless Browser-pane tab doesn't composite frames, which
  throttles/pauses requestAnimationFrame entirely, so the live animation
  loop itself could not be watched directly in this environment. A
  temporary debug hook (window.__debugTMP) used for this testing was
  removed before commit (grep-confirmed clean).
- %-based responsive layout confirmed correct via read-page/JS inspection
  at both desktop (1280x720) and mobile (375x812 emulated) viewport sizes
  -- circle/rope/floor positions and vmin-based circle radius all scaled
  proportionally, dev panel remained readable and fit the smaller
  viewport.
- node --check clean on the extracted inline script, both before and after
  removing the debug hook.
- Not verified: real touch input on an actual mobile device (viewport-size
  emulation only), and the ?dev=1/production-hostname branch of the

Fixed 3 real issues from the user's own hands-on testing of the previous
entries' work.

Fixed:
- Double-click-to-cut intermittently "just stopped working" after a few
  uses. Root cause: onPointerDown never cleared a prior holdTimer before
  starting a new one -- a pointerdown that never got a matching pointerup
  (any dropped/non-round-tripping event) orphaned its timer once the next
  pointerdown overwrote the holdTimer variable; the orphaned timer still
  fired later against whatever downInfo was current *then*, marking an
  unrelated in-progress click as a false hold and silently swallowing it
  (both punch and cut return early on info.isHold). Fixed by always
  clearing holdTimer at the top of onPointerDown.
- Cutting the rope while it was already mid-swing caused a visible freeze
  for a split moment before the swing continued -- reported directly by the
  user ("it should be getting cut while swinging, that shouldn't happen").
  Root cause: the cut-sweep animation added in the previous entry froze the
  cut piece's physics (skipped integration/floor-collision/pile-repulsion)
  for the sweep's duration. Fixed by making the sweep purely cosmetic --
  cutRopeAt() now applies the toppling tilt immediately (rotating both the
  current AND previous-frame position around the same pivot, so the tilt
  adds a topple bias without zeroing out whatever velocity the piece
  already had from the swing) and the piece integrates normally from the
  very next frame; the sweep mark (renderCutSweep()) now tracks the piece's
  own live points[0] position every frame instead of a static remembered
  point, since the piece is moving under it the whole time.
- The rope was rendering behind the circle; swapped render() to draw the
  circle first and the rope on top, per explicit request.

Verified:

  exactly the circle's color before the fix), while a pixel at the circle's

Fixed hold-to-grow missing the circle and firing a charge-punch instead,
fixed real (and self-introduced) growth jitter/stall bugs, added a Click
And Hold Distance control, and baked in 2 more rounds of user-provided
settings dumps as defaults.

Fixed:
- isOnCircle() used the circle's bare visual radius, which a real user
  found unreliable to hit precisely, especially at the current small
  Circle Size default (4.5%vmin) and with the rope rendering visually
  through/over the circle right where it emerges -- a hold "clearly meant
  for the circle" could land just outside it and get treated as a rope
  hold instead, firing an unwanted charge-punch on release. Fixed by
  adding a generous vmin(4) margin to the circle's effective hit-radius,
  used consistently for both hold-to-grow eligibility and the rope's own
  exclusion zone.
- The rope jittered slightly even when hanging still, specifically while
  growing. Root cause: setMainRopeTotalLength() re-derived segLen from
  newTotalPx/pointCount every call -- every time growth added a new point,
  pointCount jumped, so segLen (the rest-length EVERY existing segment is
  solved against) silently changed too, in the same instant, by an amount
  that didn't match the continuously-growing newTotalPx. The constraint
  solver then had one frame to correct that whole-chain mismatch, which
  read as a small bounce. Fixed by pinning segLen to exactly
  TARGET_SEG_LEN_VH permanently -- new points are already inserted exactly
  that far from their neighbor, so there's nothing left to correct.
- That fix introduced a second bug, caught by direct reproduction before
  calling it done: with segLen now constant, growRope()'s old baseline
  calculation (segLen * pointCount) stopped changing between point
  insertions, so sustained growth silently stalled for however long it
  took to cross the next whole-point threshold (confirmed directly:
  ropeLength climbed once, then sat completely frozen for 270+ simulated
  frames despite the hold still being active). Fixed by adding
  mainRope.totalLength, a persisted real-length value growRope() actually
  accumulates against, decoupled from the quantized segLen*pointCount
  product.
- cutRopeAt() wasn't updating mainRope.totalLength (or the Rope Length
  slider's displayed value) after truncating the rope -- found while
  verifying the above fix. Without this, growth after a cut would have
  resumed from the stale PRE-cut length, and nudging the Rope Length
  slider post-cut would have jumped the rope back out near its old length
  instead of adjusting the actual (shorter) current one.

Added:
- Click And Hold Distance dev control (CLICK group): gates whether
  releasing a charged hold actually fires a punch, separately from Click
  Distance (which still governs quick-tap targeting) and separately from
  the now-unlimited-by-Click-Distance charging itself -- a hold released
  too far from the rope now does nothing, rather than punching wherever
  the nearest rope point happened to be.
- Baked in 2 more rounds of user-provided Copy Settings dumps as the new
  hardcoded defaults (Rope Length, Click Distance, Click Intensity, floor
  color/thickness/height, and the built-in Dev Panel group's row order).
  Rope Length's new default (100.16051775147857 %vh) exceeded its prior
  max (90) -- raised to value*1.2 (120.19262130177428) per the project's
  standing over-max-default rule; every other provided value already fit
  its slider's existing range.
- Refactored the built-in "Dev Panel" appearance group from two separate
  arrays (sliders, then colors) into one unified, arbitrarily-orderable
  array -- needed to actually honor the requested new row order, which
  interleaves slider and color rows in a way the old two-array split could
  never represent.

Verified:
